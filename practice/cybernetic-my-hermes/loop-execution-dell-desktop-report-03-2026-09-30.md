## 6. 第五步：根因分析

### 案例 1：邮箱泄露本身（09-19 发现）

| 层级 | 分析 |
|------|------|
| 现象 | 8 个公开仓库 63~95 个提交含真实个人邮箱，跨 2019–2026 |
| 直接原因 | 仓库级 config 长期配置真实邮箱；部分仓库无 config 继承占位/旧身份 |
| 深层原因 | **规律层缺失**：无"GitHub 仓库一律 noreply"的 L1 铁律；无"push 前身份自检"闸门；2026-09-13 身份文档反而把"改为真实邮箱"写成待办建议（错误指令源） |
| **根因判定** | **规律错（L1 铁律缺失 + 文档指令错误）**，非执行错——当时所有操作都"正确地"执行了错误规则 |
| 修复 | noreply 铁律入记忆/AGENTS/身份文档；文档纪律"正文禁写真实邮箱"；push 前身份自检入维护约定 |

### 案例 2：重写不彻底（孤儿 ref + PR ref 残留）

| 层级 | 分析 |
|------|------|
| 现象 | 第一轮重写后，cybernetic 远程仍有 `refs/remotes/origin/main` 指向重写前提交（含真实邮箱）；zipbomb PR#1 的 `refs/pull/1/head` 同 |
| 直接原因 | 只 force push 了主分支，未扫全部远程 refs；PR ref 由 GitHub 托管不可删 |
| **根因判定** | **规律错（"重写完成"的验收标准定义不全）**——只验了主分支，没验"所有 ref 可达提交" |
| 修复 | 新技能 `git-privacy-rewrite` 明确验收标准：`git ls-remote` 全 ref 枚举 + 逐 ref 可达提交 grep 0 残留；PR ref 列为平台限制项并走 GitHub Support 通道 |

### 分析结论
两个根因都在规律层（铁律缺失 + 验收标准不全），无 Skill 执行缺陷。修复方式：一条新 L1 铁律 + 一个程序性技能。

## 7. 第六步：可复用提炼

1. **新建技能 `git-privacy-rewrite`**：Git 历史 PII 泄露审计与重写完整流程（双管齐下 mailmap+replace-text、WSL 链路、全 ref 验收、fork 取证、PII 工单模板）
2. **"API 不可信，clone 是铁证"**：GitHub API 对邮箱做归一化（返回 noreply 假象），PII 审计必须 clone 后 `git log --all --format='%ae|%ce'` 逐字节验证
3. **"重写完成"验收三件套**：① 主分支 grep 0 残留 ② `git ls-remote` 全 ref 枚举无孤儿 ③ 逐 ref 可达提交 0 残留——三条全过才算完成
4. **PII 处置通道**：第三方 fork 不可自行删除 → GitHub Support 工单（Security & Privacy 分类，登录态自动验证身份，工单私密）
